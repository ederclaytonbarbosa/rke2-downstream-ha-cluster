# RKE2 Downstream HA Cluster

Reference implementation for an independent ten-node RKE2 cluster that can run autonomously and later be imported into a Rancher management cluster.

## Architecture

```text
External L4 load balancer / VIP: 198.51.100.10
      |-- TCP 9345 -> three RKE2 server nodes
      |-- TCP 6443 -> three RKE2 server nodes
      |
      +-- workload-cp-01 198.51.100.11 (etcd + control plane)
      +-- workload-cp-02 198.51.100.12 (etcd + control plane)
      +-- workload-cp-03 198.51.100.13 (etcd + control plane)
      |
      +-- workload-worker-01 198.51.100.21
      +-- workload-worker-02 198.51.100.22
      +-- workload-worker-03 198.51.100.23
      +-- workload-worker-04 198.51.100.24
      +-- workload-worker-05 198.51.100.25
      +-- workload-worker-06 198.51.100.26
      +-- workload-worker-07 198.51.100.27
```

The server nodes are tainted for critical add-ons so application workloads are scheduled on the seven worker nodes. The cluster remains fully usable without Rancher; importing it only adds centralized lifecycle visibility and access control.

## What this project demonstrates

- Three-node embedded-etcd and control-plane quorum
- Seven dedicated worker nodes
- Fixed registration endpoint and Kubernetes API endpoint
- Separate server and agent automation
- Runtime-only cluster tokens with no committed credentials
- Control-plane taints and worker labels
- Cluster topology, readiness, and scheduling validation
- Rancher import workflow without rebuilding the cluster
- etcd snapshot and operational guidance

## Deployment summary

1. Prepare DNS and the external load balancer.
2. Generate an RKE2 token on a trusted host.
3. Bootstrap `workload-cp-01` with `CLUSTER_INIT=true`.
4. Join `workload-cp-02` and `workload-cp-03` through port 9345.
5. Join all seven workers using `scripts/install-agent.sh`.
6. Validate the topology with `scripts/validate-cluster.sh`.
7. Optionally import the cluster into Rancher using the commands generated by Rancher.

The IP addresses are reserved documentation values. The `titechsolucoes.com.br` hostnames are deployment parameters owned by the project author.

## Bootstrap the first server

```bash
export RKE2_TOKEN="$(openssl rand -hex 32)"

sudo --preserve-env=RKE2_TOKEN \
  NODE_NAME=workload-cp-01 \
  NODE_IP=198.51.100.11 \
  TLS_SANS=rke2-workload-api.titechsolucoes.com.br,198.51.100.10 \
  CLUSTER_INIT=true \
  bash ./scripts/install-server.sh
```

## Join additional servers

```bash
sudo --preserve-env=RKE2_TOKEN \
  NODE_NAME=workload-cp-02 \
  NODE_IP=198.51.100.12 \
  RKE2_SERVER=https://rke2-workload-api.titechsolucoes.com.br:9345 \
  TLS_SANS=rke2-workload-api.titechsolucoes.com.br,198.51.100.10 \
  bash ./scripts/install-server.sh
```

Repeat for `workload-cp-03`.

## Join worker nodes

```bash
sudo --preserve-env=RKE2_TOKEN \
  NODE_NAME=workload-worker-01 \
  NODE_IP=198.51.100.21 \
  RKE2_SERVER=https://rke2-workload-api.titechsolucoes.com.br:9345 \
  NODE_LABELS=workload-tier=general,node-pool=worker \
  bash ./scripts/install-agent.sh
```

Repeat with unique names and addresses for workers 02 through 07.

## Validate and import

```bash
export KUBECONFIG="$PWD/rke2-workload.yaml"
bash ./scripts/validate-cluster.sh
```

Then follow [docs/import-to-rancher.md](docs/import-to-rancher.md).

## Security notes

- Never commit tokens, kubeconfigs, private keys, or Rancher import manifests.
- Review any Rancher-generated import command before executing it.
- Limit ports `9345`, `6443`, and embedded-etcd traffic to trusted sources.
- Store etcd snapshots in protected external storage.
- Pin and test RKE2 versions before production upgrades.
